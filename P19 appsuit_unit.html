앱이 아니라, 그 안의 라이브러리가 먼저 공격 대상이 됩니다.
.so / .jar 파일은 앱 외부에 배포되는 순간 누구나 분석할 수 있으며,
전용 보호 솔루션 없이는 핵심 알고리즘과 SDK 구조가 그대로 노출됩니다.

STAGE 01 · 분석
외부 라이브러리 분석을 통한 로직 탈취
.so, .jar 파일을 역공학으로 분석하여 핵심 알고리즘과 인증 로직을 탈취합니다.
STAGE 02 · 노출
SDK 및 API 구조 역공학
배포된 SDK 내부 구조를 분석하여 API 호출 방식과 내부 로직을 파악하고 악용합니다.
STAGE 03 · 변조
위·변조를 통한 악성 코드 삽입
보호되지 않은 라이브러리를 변조하여 악성 코드를 삽입하고 앱 전체를 감염시킵니다.
STAGE 04 · 확산
제3자 라이브러리 보안 취약
납품된 3rd-party 라이브러리가 해킹되면 해당 라이브러리가 적용된 모든 앱이 연쇄적으로 위험에 노출됩니다.

자주 묻는 질문
어떤 라이브러리 파일을 보호할 수 있으며, 기존 개발 환경을 변경해야 하나요?
+
Android 환경의 .so 네이티브 라이브러리와 .jar 라이브러리, SDK 파일, API 모듈 등 핵심 코드 자산 전반을 보호합니다. 결제·인증 SDK처럼 외부 납품되는 라이브러리, 자사 핵심 알고리즘 라이브러리, 3rd-party 라이브러리까지 동일한 수준으로 적용 가능합니다.
적용 방식은 웹 서비스 업로드/다운로드 방식이라 별도 SDK 연동이나 빌드 환경 변경이 필요하지 않습니다. 라이브러리 파일을 업로드 → 보안 옵션 설정 → 보안 적용된 파일 다운로드의 3단계로 완료되며, 기존 빌드 파이프라인에 그대로 교체만 하면 즉시 보호가 시작됩니다.
보안 적용 후 앱 성능에 영향이 있나요?
+
Unit은 빌드 단계에서 라이브러리에 보안을 적용하는 구조이기 때문에 런타임 성능에 영향을 주지 않습니다. 식별자·문자열·API 호출부의 난독화는 코드 구조만 변경할 뿐 실행 로직 자체에는 영향이 없으며, .so 파일 암호화 역시 실행 시 자동 복호화되어 정상 동작합니다.
삼성전자, LG전자, 이니텍 등 대규모 서비스 환경에서 적용된 사례를 통해 안정성이 검증되었으며, 결제·인증 SDK처럼 성능에 민감한 영역에도 무리 없이 적용되고 있습니다.
기존 코드에 영향을 주지 않나요?
+
기존 소스코드는 전혀 수정할 필요가 없습니다. Unit은 컴파일된 .so / .jar 라이브러리 파일을 직접 처리하는 방식이라, 보안이 적용된 라이브러리 파일로 교체만 하면 됩니다.
API 호출 방식, 클래스 구조, 인터페이스가 모두 그대로 유지되므로 라이브러리를 사용하는 앱 코드도 변경할 필요가 없으며, CI/CD 파이프라인에도 라이브러리 교체 단계만 추가하면 적용이 완료됩니다.
3rd-party 납품 시에도 납품받는 측에서는 보안이 적용되었는지 의식하지 않고 평소처럼 사용할 수 있습니다.
